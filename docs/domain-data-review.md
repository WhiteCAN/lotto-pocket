# 도메인·데이터 계층 독립 검토

검토일: 2026-09-18  
범위: `domain/LottoRules.kt`, `data/DrawCodec.kt`, `data/LottoDatabase.kt`, `data/LottoRepository.kt`  
기준: `docs/superpowers/specs/2026-09-18-lotto-pocket-design.md`

## 발견 사항

아래는 수정 전 검토 기록이다. 이후 백업 크기 제한, 빈도 0 제외, 추천 문맥 스냅샷, 균등 조합 순위 선택, 중복 회차 처리, 누락 옵션 보존을 수정했고 자동 테스트를 통과했다. 용지 식별자 기반 복수 구매 수량 관리는 첫 버전에서 지원하지 않으며 회차+번호 중복 제거 방식과 한계를 README에 명시했다. 현재 상태는 implementation-progress.md를 참조한다.

### P1 — 앱이 만든 백업을 앱이 복원하지 못할 수 있음

`LottoRepository.exportBackup()`은 게임 수와 무관하게 전체 DB를 내보내지만 크기를 제한하거나 경고하지 않는다(`LottoRepository.kt:25-32`). 반면 모든 가져오기는 `DrawCodec.decode()`를 먼저 거쳐 UTF-8 5MB를 초과하면 즉시 거부된다(`DrawCodec.kt:12-14`, `LottoRepository.kt:34-35`). 기록이 누적되어 백업이 5MB를 넘으면 정상적으로 내보낸 개인 기록을 같은 앱에서 복원할 수 없다. 내보내기 전에 복원 가능 크기를 보장하거나, 개인 백업과 추첨결과 가져오기의 제한을 분리해야 한다.

### P1 — 빈 통계도 고빈도 번호가 있는 것처럼 복원함

`frequencies()`는 사용 가능한 과거 회차가 없어도 1~45를 모두 빈도 0으로 반환하고 번호 오름차순으로 정렬한다(`LottoRules.kt:60-69`). `candidates()`는 이 결과의 상위 N개 또는 구매번호 내부 상위 N개를 그대로 복원한다(`LottoRules.kt:42-51`). 따라서 DB가 비어 있을 때 전체 모드는 구매번호 1~10 등을, 구매번호 내부 모드는 작은 번호 N개를 “빈도 복원”한다. 설계의 “실제 빈도가 없으면 표시하지 않음” 및 “해당 후보가 없으면 복원 0개”와 충돌한다. 표본 회차가 0이면 복원 집합을 비워야 한다.

### P1 — 추천 스냅샷이 결과를 재현할 핵심 문맥을 잃음

`GameRecord`는 `options`, `fixed`, `locks`만 저장하고 `statisticsThroughRound`와 추천에 사용한 `sourceTicketIds`가 없다(`LottoDatabase.kt:12-17`). 설계는 추천 기록이 통계 기준 회차와 원본 용지를 유지하도록 요구한다. 이후 추첨 데이터나 선택 용지가 바뀌면 저장된 추천이 어떤 데이터로 만들어졌는지 설명하거나 동일 조건을 복원할 수 없다. 추천 배치 단위 스냅샷에 두 값을 보존해야 한다.

### P1 — 대량 백업에서 논리적으로 중복된 개인 기록을 식별할 수 없음

복원 충돌 검사는 `GameRecord.id`만 기준으로 한다(`LottoRepository.kt:53,57-60`). 서로 다른 ID를 가진 동일 용지/동일 게임은 모두 삽입된다. 현재 스키마에는 Ticket과 원본 QR 식별값 또는 중복 판정용 fingerprint가 없어 “같은 용지 재스캔 경고 및 중복 제외 방지”를 데이터 계층에서 보장할 수 없다. 단순히 번호가 같은 서로 다른 실제 구매를 합치면 안 되므로, 게임 번호가 아니라 원본 용지 식별자 단위로 해결해야 한다.

### P2 — 조합 가능 수를 먼저 계산하지 않고 편향된 폴백을 사용함

`generate()`는 가능한 조합 수를 계산하지 않고 무작위 시도를 256회 한 뒤 사전식 첫 조합을 전수 탐색한다(`LottoRules.kt:113-116,172-205`). 막힌 조합 비율이 높으면 폴백 결과가 작은 번호 쪽으로 편향되어 “최종 후보에서 균등한 비복원 추출”을 깨뜨린다. 큰 후보 공간에서는 실패를 판정하기 위해 많은 조합을 순회할 수도 있다. `C(선택 가능 수, 필요한 수)`에서 금지 조합 수를 빼 요청 수 가능 여부를 먼저 확인하고, 허용 조합을 균등하게 선택해야 한다.

### P2 — 도메인 빈도 계산은 중복 회차 입력을 중복 집계함

파일 디코더와 Room PK는 중복 회차를 막지만 `frequencies()` 자체는 같은 회차가 두 번 들어온 목록을 그대로 합산한다(`LottoRules.kt:60-66`). 저장소 외 호출이나 병합 과정의 실수로 통계가 조용히 왜곡될 수 있다. 회차 중복을 거부하거나 회차별 동일 데이터임을 확인한 뒤 한 건만 집계해야 한다.

### P2 — 옵션이 빠진 백업은 현재 사용자 설정을 기본값으로 덮어씀

백업의 `options`가 없으면 문자열 `{}`를 만들고 기본 옵션으로 검증한 뒤(`LottoRepository.kt:54-55`) 트랜잭션에서 현재 `settings.options`를 `{}`로 교체한다(`LottoRepository.kt:61`). 누락 필드를 이전 형식 호환으로 허용할 경우 현재 설정을 보존해야 하며, 필수 필드라면 쓰기 전에 명시적으로 거부해야 한다.

## 확인된 정상 동작

- 추첨결과 파일은 5MB, schemaVersion, 회차 중복, 날짜, 번호 범위·고유성, 보너스 중복을 전체 검증한 뒤 저장한다.
- 기존 회차와 번호·날짜가 충돌하면 새 회차까지 포함한 가져오기 전체가 롤백된다.
- 백업의 게임·옵션은 트랜잭션 진입 전에 파싱·검증되고, 동일 ID의 내용이 다르면 게임·추첨결과·설정 모두 쓰기 전에 거부된다.
- 고정번호 우선 복원, 미래 회차 제외, 보너스 제외 빈도, 동률 번호 오름차순, 잠금 유지, 구매/추천 완전 동일 조합 차단은 구현되어 있다.

코드와 DB는 변경하지 않았고 Gradle도 실행하지 않았다.
